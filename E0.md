# ProjectHub - Bootstrap E0 et SLICE-00

> **Démonstrateur technique expérimental, données exclusivement synthétiques.** Ce code ne valide pas les ADR, ne constitue pas un SaaS ni un pilote E1, et ne doit pas recevoir des données réelles. Démarrage formel E0 soumis à [ACT-03 et aux approbations d'architecture](docs/07-architecture/02-architecture-authority-register.md).

## 1. Périmètre

- `backend/` : Django 5.2 LTS, DRF, PostgreSQL, sessions authentifiées, CSRF et API tenant-scoped. `Organization` est la frontière de confidentialité.
- `frontend/` : Next.js 16, React 19, TypeScript, UI de sélection du contexte et de tests de refus.
- `infra/initdb/` : deux rôles SQL distincts : `ph_migrate` (migrations) et `ph_app` (runtime, non propriétaire des tables, sans superuser ni BYPASSRLS).
- `poc/rls/` : comparaison isolée R-0/R-1. **Aucune policy RLS n'est activée sur les tables Django dans SLICE-00 tant que l'ADR n'est pas accepté.**
- `SLICE-00` couvre `PH-BLG-001..009`. Project/WorkItem sont des sentinelles techniques et ne constituent pas la livraison fonctionnelle de `SLICE-01`.

## 2. Exécution locale via Docker Compose

Prérequis : Docker Engine + Compose v2. Aucun compte réel ni fichier privé.

```bash
cp .env.example .env
# Remplacer les quatre exemples par des valeurs aléatoires locales, alphanumériques.
docker compose up --build
# Dans un navigateur : http://localhost:3000
```

L'accès depuis l'extérieur de la machine est limité par `127.0.0.1:3000:3000`. Aucun port PostgreSQL ou Django n'est publié. Les secrets restent dans `.env` ignoré par Git. Ne pas exposer ce démonstrateur sur Internet.

Identifiants **fictifs uniquement** : `demo_alice` (A), `demo_bob` (B), `demo_both` (A+B), `demo_admin_a`, `demo_admin_b`, `demo_viewer`, `demo_revoke`, `demo_guest`. Le mot de passe partagé de cette base jetable est défini par `E0_DEMO_PASSWORD`, sinon reconstruit à l'exécution depuis les fragments publics `e0`, `demo` et `only`. Aucune organisation réelle n'est impliquée.

La première initialisation migre la base sous `ph_migrate`, puis exécute le seed sous `ph_app`. Le seed est idempotent et refuse de s'exécuter si `E0_SYNTHETIC_ONLY` n'est pas activé. Pour **réinitialiser complètement** les données de démonstration (destructif uniquement sur ce volume local) :

```bash
docker compose down --volumes
docker compose up --build
```

## 3. Parcours A/B à démontrer

1. Se connecter en `demo_alice`, voir uniquement `Demo-Org-A` et son Workspace ; B doit être absent de la liste.
2. Sélectionner A, voir uniquement `Projet fictif A` et `Action fictive A`.
3. Tenter un GET par ID du Project B : HTTP 404 ; tenter une approbation sans mandat : HTTP 403.
4. Se reconnecter avec `demo_both`, sélectionner A puis B explicitement et vérifier qu'aucune donnée A ne survit à la sélection B.
5. En `demo_viewer`, lire A mais refuser toute mutation d'objet.
6. En `demo_admin_a`, révoquer `demo_revoke`. Sa session déjà ouverte doit perdre immédiatement accès aux endpoints A ; l'événement d'audit reste présent.
7. Exporter JSON du contexte A et rechercher toute trace de B : aucune.

Les routes `/api/*` sont servies via Next.js comme reverse proxy same-origin. Les vérifications sont appliquées dans DRF et par les contraintes composées PostgreSQL, pas par le frontend.

## 4. Commandes de preuve

Dans un environnement jetable PostgreSQL 16 configuré, en mode E0 uniquement :

```bash
python -m pip install -r backend/requirements.txt
cd backend
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --noinput
python manage.py test foundation --verbosity 2
python manage.py seed_e0
cd ..
cd frontend
npm ci
npm run typecheck
BACKEND_INTERNAL_URL=http://127.0.0.1:8000 npm run build
npm run start
```

Les variables `DATABASE_URL`, `DJANGO_SECRET_KEY` et `E0_SYNTHETIC_ONLY=1` doivent être définies et pointées vers des instances de **test uniquement**.

La CI `.github/workflows/e0-foundation.yml` provisionne PostgreSQL, exécute le POC, les migrations et les tests Django, compile Next et lance un smoke HTTP sur `/api/`. Dans Compose, Django est servi par Gunicorn WSGI sans autoreload ; `/api/health/` teste la vie du processus et `/api/ready/` effectue une requête réelle à PostgreSQL. Le job Compose vérifie trois démarrages propres avec volumes synthétiques neufs, session/CSRF, refus inter-tenant et export pour chacun. Aucun résultat HTTP 500 ou refus inattendu n'est retenté automatiquement. Consulter les preuves du workflow sur le SHA exact.

## 5. Limites et décisions à prendre

- Pas de pilote réel ni de déploiement public, authentification de démonstration avec mots de passe connus, `DEBUG=1` uniquement en environnement local fermé.
- Pas de comptes institutionnels, secrets réels, sauvegarde de production, throttling d'authentification, ni engagements E1.
- `ADR-0004` et `ADR-0005` restent à approuver ; `ADR-0019` compare R-0/R-1 et recommande `R-2` en attente de l'autorité GOV-02.
- Une compilation ou un test réussi ne prouve pas l'adéquation fonctionnelle, la sécurité de production ni les huit gates E1.
- Les dépendances frontend directes et transitives sont figées dans `frontend/package-lock.json` ; `npm ci` échoue si `package.json` et ce lockfile divergent.

Voir le [registre de décision RLS](docs/07-architecture/03-adr-0019-rls-poc-decision.md) et le [plan d'architecture](docs/07-architecture/00-adr-tenancy-permissions-pre-e0-plan.md).
